# Recipe の写真の扱い

Recipe の写真をどう選び、どこに置き、いつ消すかの検討をまとめたファイルです。
写真はまだ実装していません。
写真を実装する PR では、このファイルを読んでから着手します。
実装して方針が固まったら、残すべき方針を [architecture.md](architecture.md) に移し、このファイルは消します。

このファイルは、architecture.md の写真の部分を詳しくしたものです。
層の分け方や失敗の扱いは、architecture.md の「UseCase の方針」「データ層の方針」に従います。
このファイルと architecture.md が食い違ったら、architecture.md を正とします。

各項目には、次の印を付けています。

- **決定**：そうすると決めた
- **方針**：現時点の意思として決めた。根拠は意思で、計測や実装の結果で覆りうる
- **保留**：今は決めないと決めた。今決めなくてよい理由と、決めるときの材料を書く
- **想定**：決めてはいないが、今のところそのつもりで進めている
- **未決**：まだ判断していない

## 言葉

- **アプリ専用フォルダ**：Android の `filesDir`、iOS の Application Support のように、アプリだけが読み書きでき、OS が勝手に消さない場所。キャッシュ用フォルダ（Android の `cacheDir`、iOS の Caches）もアプリだけの領域だが、容量が足りないと OS が消すので、このファイルでは含めない
- **仮置き**：選んだ写真を、Recipe を保存するまで置いておく場所とそのファイル。Recipe からはまだ参照されない
- **本番の場所**：Recipe の写真として使うファイルを置く場所
- **アプリが落ちる**：クラッシュ、OS による終了、ユーザーによる終了のどれも含む。どれでも、メモリの中身は消え、ファイルは残り、ViewModel が破棄されるときの処理は呼ばれない
- **起動の処理**：アプリのプロセスが始まってから、最初の画面を表示するまで。Android で画面が開き直された場合は、その画面を表示するまで

## 想定している流れ

1. 編集画面で、写真を選ぶ（または撮る）
2. 写真を、アプリ専用フォルダの中の仮置きの場所にコピーする（決定）
   - 編集画面の状態は、画像のデータを持たず、写真を指す ID だけを持つ。Recipe に今入っている写真なら本番の写真の ID、新しく選んだ写真なら仮置きの写真の ID（決定）
3. 写真を選び直す、写真を削除する、保存せずに編集画面を閉じる、のどれかが起きたら、その場で仮置きを消す（決定）
4. 保存ボタンを押したら、「仮置きの写真を本番の場所に置く → Recipe を保存する → 古い写真を消す」の順に進む（想定）
   - 本番の場所に置くとき、仮置きを移すかコピーするかは未決
5. Recipe の保存に失敗したら、もう一度保存できるように仮置きを残す（決定。残す方法は未決）

写真も、名前・状態・メモと同じく、編集画面の保存ボタン1回でまとめて反映すること（想定）を前提にしています。
本番の場所もアプリ専用フォルダの中に置くこと（想定）を前提にしています。

## 決めたこと

### 選んだ写真は仮置きにコピーし、保存のときに本番の場所に置く（決定）

保存ボタンを押すまで写真を手元に置くには、OS から期限付きで届いた写真を、アプリが自分の場所へ写し取る必要があります（下の前提になる事実）。
写し取る先として、次の4つを、同じ場面（写真 old を持つ Recipe を編集し、写真 X を選び、Y に選び直して保存する）で比べました。

- **A. 画像のデータを、そのままメモリ（ViewModel）に持つ**
  - 選び直す・削除する・閉じる・落ちる、のどの場面でも写真はメモリから自然に消え、アプリが消す処理は要らない
  - 保存に失敗しても、写真はメモリに残る
  - Android でアプリが裏で終了させられたとき、選んだ写真は戻せない。退避先（SavedStateHandle）に画像のデータは入らないため
  - 編集中は、画像のデータを画面の状態として持ち続ける（縮小すれば数百 KB 程度の見込み）
- **B. 選んだ瞬間に、本番の場所へコピーする**
  - 保存ボタンで写真を置く処理が無く、保存に失敗しても写真は何もしなくても残る
  - 選び直す・削除する・閉じる場面では、アプリがその場で消す必要がある
  - 落ちたときの残骸が本物の写真と同じ場所に混ざり、片付けるには DB の全 Recipe の写真 ID と照らし合わせる必要がある
- **C. 選んだ瞬間に仮置きの場所へコピーし、保存ボタンで本番の場所に置く**
  - 選び直す・削除する・閉じる場面では、アプリがその場で消す必要がある（B と同じ）
  - 落ちたときの残骸は仮置きの場所にだけ残り、DB と照らし合わせずに、作られた時刻などの条件だけで消せる
  - 落ちたときに写真を戻すなら、ID を退避すれば仮置きのファイルから戻せる
  - Recipe の保存に失敗したときに仮置きを残す方法を、別に決める必要がある（本番の場所に置くときに仮置きを移すと、仮置きはもう無いため）
- **D. ギャラリーの元の写真を、コピーせずに参照し続ける**
  - ギャラリーで元の写真を消したり編集したりすると、Recipe の写真も消えたり変わったりする
  - クラウドにしか無い写真は、表示のたびに取得が要ることがある
  - 同期や別の端末で見るときは、結局どこかで画像のデータを読んでアップロードする必要がある
  - カメラで撮った写真はギャラリーに無い
  - Android は読み取り権限を延ばせる件数がアプリ全体で 5,000 件まで、iOS は許可を求めるダイアログが出る

ユーザーが、A・B・C の表を比べたうえで C を選び、D を示した後も C を維持しました。
ユーザーは、C を選んだ決め手を述べていません。
表から読み取れる C の利点は、落ちたときの残骸が本物の写真と混ざらないこと、落ちたときに写真を戻す選択肢を残せること（戻すかは保留）です。
代償は、保存に失敗したときに仮置きを残す方法が要ることです。

なお、最初に C が選ばれた時点では、A の欠点として「画像のデータは数 MB になる」「data class の同値の判定が素直に動かない」が挙がっていました。
これは言い過ぎで、縮小すれば数百 KB 程度、同値の判定も選ぶたびに新しいデータになるので決定的な問題ではない、と後で訂正しています。
訂正の後に表を並べ、ユーザーは C を維持しました。

仮置きの場所は、アプリ専用フォルダの中にします（決定）。
OS が勝手に消さず、仮置きが消えるのはアプリが消したときだけになるためです。
キャッシュ用フォルダにすると、アプリが消し損ねた分もいずれ OS が片付けますが、編集中に消えることがまれにあり、その扱いが要ります。
写真を実装するときに、キャッシュ用フォルダにする案も含めて見直してよい、とユーザーが決めています。

ユーザーがギャラリーで元の写真を消したり編集したりしても、Recipe の写真は変わりません。

### 仮置きは、不要になったと分かった場面でその場で消す（決定）

| 場面 | アプリに分かるか | 仮置きの扱い |
|---|---|---|
| 写真を選び直した | 分かる | 前の仮置きを消す |
| 選んだ後に「写真を削除」を押した | 分かる | 消す |
| 保存せずに編集画面を閉じた | 分かる（ViewModel が破棄されるとき） | 消す |
| 保存に成功した | 分かる | 残さない（移したなら何もしない、コピーしたなら消す） |
| 保存に失敗した | 分かる | もう一度保存できるように残す |
| 編集中にアプリが落ちた | 分からない | 後で掃除する（下の「まだ決めていないこと」） |

起きた瞬間に分かる場面は、その場で処理すれば確実に片付く、とユーザーが判断しました。
ViewModel が破棄されるときの扱いは、CMP の iOS 版で Android と同じかが未確認です。

### 起動の処理の中では、写真を削除しない（方針）

起動速度を落としたくない、というユーザーの意思によるものです。
どれだけ遅くなるかは測っていません。
落ちたときに残る仮置きや本番の場所の写真の掃除にも、この方針を当てはめます。
実装して計測し、起動の処理の中で消しても影響が無視できると分かったら、見直してよいです。

掃除のタイミングの候補として、次を挙げています。

- 最初の画面を出した後に、裏で消す。処理はファイルの一覧を取ることと、DB から写真 ID を1回読むことだけで、写真が数百枚程度なら体感できる負荷にはならない見込み（測っていない）
- Recipe の保存に成功した後に消す
- アプリが裏に回ったときに消す
- OS の定期実行の仕組みを使う（Android の WorkManager、iOS の BGTaskScheduler）。Android と iOS で別々の実装になる

起動の後に掃除するので、同時に起きる操作に気をつける必要があります。

- 本番の場所の掃除と保存：本番の場所に置いた直後、Recipe を保存する前の写真は、まだどの Recipe からも使われていないので、掃除が走ると消してしまう。掃除と保存を順番待ちにするか、保存ボタンを押せる状態になる前に済ませる
- 仮置きの掃除と写真を選ぶ操作：掃除の前に新しく選んだ写真も仮置きに入るので、今回の起動より前に作られたものだけを消す、などの条件で区別する

### 写真は縮小できるならしたい（方針）

撮ったままの写真は1枚あたり数 MB になります（目安）。
縮小すれば、端末の容量と、後でサーバーに上げるときの通信が軽くなり、代わりに拡大したときの細かさが落ちます。
ユーザーは、縮小できるならしたいが、どこまで縮小できるかは UI に表示して動かしてみないと分からない、と述べています。
どこまで縮小するかは、UI に表示して確かめてから決めます。

## 今は決めないと決めたこと

### Android で裏で終了させられたときに、選んだ写真を戻すか（保留）

編集中に写真を選び、保存せずに別のアプリへ切り替えている間に、Android がアプリを終了させることがあります。
ユーザーが戻ると、Android は編集画面を開き直しますが、メモリは消えています。
iOS は、標準では終了させたアプリの画面を開き直しません。
Android でも、ユーザーがアプリを終了させた場合は最初の画面から始まります（クラッシュした場合も同じと考えているが未確認）。

- **戻さない**：写真は元の写真に戻り、ユーザーは選び直す。退避した ID が無いので、「ID はあるのに仮置きが無い」場合の扱いは要らない
- **戻す**：仮置きの写真の ID を SavedStateHandle に退避し、開き直したときに仮置きのファイルから戻す。起動の後の掃除で、戻す予定の仮置きを消さない条件（作られてから一定時間以上たったものだけ消す など）と、仮置きが無かったときの表示と保存の扱いが要る

今決めなくてよい理由：どちらを選んでも、名前・状態・メモの編集には影響しません。
写真を実装するときに決めます。
「戻さない」で作った後に「戻す」に変える場合も、足すのは次の3つで、作り直しは要りません。

- 仮置きの ID を退避し、開き直したときに戻す処理
- 仮置きを掃除する条件（今回の起動より前のものを消す → それに加えて、一定時間以上たったものだけ消す）
- 「仮置きが無い」という結果。本番の場所に置く処理を UseCase が持つなら、編集の UseCase の結果に足す。足すと受け取る `when` がコンパイルエラーになるので、対応漏れはビルドで分かる

決めるときの確かめ方：

- Android のテスト：ViewModel を、仮置きの ID が入った SavedStateHandle で作り、写真が戻った状態になるかを確かめる
- Android の実機：アプリを裏に回し、`adb shell am kill <パッケージ名>` で終了させ、最近使ったアプリの一覧から戻る。開発者向けオプションの「アクティビティを保持しない」は画面を破棄するだけでプロセスを終了させないので、この確認には足りない
- iOS のシミュレーター：アプリを裏に回して終了させ（Xcode の停止、または `xcrun simctl terminate`）、起動し直す。最初の画面から普通に始まることと、CMP の iOS 版で SavedStateHandle の値が戻るか（未確認）を確かめる
- どちらの結果でも、「退避した ID が無い」場合と「ID はあるのに仮置きが無い」場合を扱えていれば不具合にはならない

### 保存の途中で落ちたときに本番の場所に残る写真の掃除（保留：今は作らない）

保存ボタンの手順の途中で落ちると、どの Recipe からも使われない写真が本番の場所に1枚残ることがあります。
本番の場所に置いた後、Recipe を保存する前に落ちると新しい写真が、Recipe を保存した後、古い写真を消す前に落ちると古い写真が残ります。

片付けるには、本番の場所のファイルを DB の全 Recipe の写真 ID と照らし合わせて、使われていないものを消します（GC と同じ考え方）。
そのために、全 Recipe の写真 ID を読む処理を Repository に足し、保存と同時に走らないようにする必要があります。

今は作らない理由：起こることはまれで、困るのは容量を少し使うことだけです。
後から作るときに足すのは、掃除の処理と Repository の読む処理が中心です（掃除と保存を順番待ちにするなら、保存の処理にも手が入ります）。
ユーザーが後回しを選びました。
使われない写真が容量の問題になったとき、または同期などで写真の保存の仕組みを大きく変えるときに作ります。

### 写真を選ぶ・撮る UI に、ライブラリを使うか自作するか（保留）

- **FileKit**：KMP / CMP 用。ピッカー、アプリのフォルダ（`FileKit.filesDir`）、画像の圧縮、表示用の Coil との連携がある。まだ 0.x。カメラに対応しているかは README では確認できていない（リリースノートに iOS のカメラ表示の修正があるので、対応していると思われる）
- **Peekaboo**：CMP 用。ピッカーとカメラ、縮小・圧縮に対応
- **自作**：選ぶのは写真1枚だけなので、各プラットフォームのピッカーとカメラの UI を抽象化して作れる。画像まわりは、実装の重さが見積もれていない

FileKit が 0.x であること、カメラも扱う必要があること、画像まわりの実装の重さが見積もれないことから、自作も選びうるという留保を持っておく、とユーザーが判断しました。
写真の UI を実装するときに、FileKit がカメラに対応しているか、iOS のカメラで撮った写真がどの形で届くか、自作の手間を比べて決めます。

## 写真の実装に着手するときに決めること

上の保留の3つと、下の「まだ決めていないこと」に加えて、次も決めます。

- どこまで縮小するか
- 仮置きの場所を見直すか
- 写真を、名前・状態・メモと同じ編集の UseCase に足すか

最初に「どこで写真を実装するか」と「本番の場所に置く処理をどこが持つか」を決めると、他の多くが絞られます。

- 「どこで写真を実装するか」で、UI と data 層まで作るのか、domain と UseCase の部分だけを先に作るのかが決まる
- 「本番の場所に置く処理をどこが持つか」で、次が決まる、または絞られる
  - 編集の UseCase が写真をどう受け取るか
  - 仮置きへのコピーと削除をどの層が持つか、仮置きの ID を誰が振るか
  - 写真の失敗をどの型で表すか、Repository を分けるか
  - 保存に失敗したときに仮置きを残す方法を、どの層で書くか
- 写真の参照を値クラスにするかは、仮置きの ID と本番の ID を区別する必要があるかで決まるので、上の2つの後に決める

### 議論したが、決めていないもの（未決）

**仮置きの写真を本番の場所に置く処理と、古い写真を消す処理を、どこが持つか**

- UseCase が持つ
  - 写真のファイルを扱う interface を domain に足し、UseCase はそれと Recipe の Repository の2つを使う
  - 手順の順序と、途中で失敗したときの扱いが UseCase に書かれ、テストで確かめられる
  - 写真に関する失敗が UseCase の結果に加わる
  - UseCase は写真を「そのまま」「差し替え（仮置きの ID）」「削除」の3種類で受け取る形になる。`String?` で受け取ると、今の本番の ID か仮置きの ID かを見分ける必要が出る
- data 層（Recipe の Repository の実装）が持つ
  - 保存の中で、写真が変わったかを判断して、ファイルを本番の場所に置いたり古い写真を消したりする
  - Recipe の `photoRef` は本番の写真を指すものなので、新しく選んだ仮置きの写真を Recipe に入れて渡すことはできない。保存に何を渡すかを決める必要がある
  - 「Recipe を保存する」処理の中にファイルの操作が入り、保存の失敗とファイル操作の失敗が混ざる。手順の順序や途中で失敗したときの扱いが、UseCase からは見えなくなる
- UI（ViewModel）が持つ
  - 保存ボタンを押したときに、ViewModel が仮置きの写真を本番の場所に置き、UseCase を呼び、成功したら古い写真を消す
  - UseCase は本番の写真の ID を受け取って保存するだけになる
  - ViewModel が保存先を知り、本番の場所に置く処理の失敗と、Recipe の保存に失敗したときに置いた写真をどうするかも扱う
  - architecture.md の「ViewModel は例外を catch せず、結果を UiState に変えるだけにする」とぶつかる。採るなら、その方針を見直す必要がある

**Recipe の保存に失敗したときに、仮置きを残す方法**

- 移した写真を仮置きへ戻す：ファイルは常に1つ。戻す処理そのものが失敗したときの扱いが要る
- 移さずにコピーし、Recipe の保存に成功してから仮置きを消す：失敗したときは何もしなくても仮置きが残る。成功した後の仮置きの削除に失敗すると、仮置きに残骸が出る

**編集中にアプリが落ちたときに残る仮置きを、いつ、どの条件で掃除するか**

- 起動の処理の中では消さない（方針）。タイミングの候補は上の「起動の処理の中では、写真を削除しない」にある
- 掃除の前に新しく選んだ写真を消さない条件が要る。例えば、今回の起動より前に作られた仮置きだけを消す
- 落ちたときに写真を戻すことにした場合は、さらに、戻す予定の仮置きを消さない条件が要る

**写真の参照に何を入れるか、どの型にするか**（Recipe の `photoRef: String?` に入れる値）

- アプリが振る ID（例：`3f2a9c`）：ファイル名やフォルダの構成が変わっても DB の値は変わらない。後でサーバーに上げても、同じ ID でサーバー上の写真を指せる。画面に表示するには、ID からファイルの場所を求める処理が要る（どこに置くかは未議論）
- 相対パス（例：`photos/3f2a9c.jpg`）：iOS の更新でも壊れない。フォルダの構成が DB に入るので、構成を変えると保存済みの値も直す必要がある
- 絶対パス：使えない（下の前提になる事実を参照）

型を、他の ID と同じく文字列を包む値クラスにするかも決めていません。
値クラスにすると、仮置きの ID と本番の ID を型で区別できます。

## 前提になる事実

2026-10-05 に調べたものです。
「未確認」と書いたものは、調べていないか、出典で確かめられていません。

- 写真は、OS から期限付きで届く
  - iOS のピッカー（PHPicker）は、写真を一時ファイルで渡し、受け取りの処理が終わると OS がそのファイルを消す。その処理の中で、自分の場所へコピーする必要がある（[Apple Developer Forums](https://developer.apple.com/forums/thread/652695)）
  - Android の写真ピッカーが返すのは、ファイルのパスではなく `content://` の URI。標準では、端末の再起動かアプリの停止までしか読めない。`takePersistableUriPermission` で読める期間を延ばせるが、アプリ全体で最大 5,000 件までで、超えると古いものから無効になる（[Photo picker | Android Developers](https://developer.android.com/training/data-storage/shared/photo-picker)）
  - Android のカメラ（撮影を他のアプリに頼む方法）は、アプリが用意したファイルに写真を書き込む
  - iOS のカメラで撮った写真がどの形で届くかは、調べていない
- アプリがいつでも読み書きできるのは、アプリ専用フォルダだけ。ギャラリーの写真は OS が管理していて、アプリが直接ファイルとして開くことはできない。ピッカーで選ばれた写真だけを期限付きで読める
- ギャラリーの元の写真を参照し続けるには、Android は URI の読み取り権限を延ばす。iOS は写真ライブラリへのアクセスの許可をユーザーから得て、写真の識別子（`localIdentifier`）を持つ。許可を求めるダイアログが出て、ユーザーは選んだ写真だけを許可することもできる
- iOS では、アプリを更新するとアプリのフォルダの絶対パスが変わる。中のファイルは残るが、絶対パスを保存していると見つからなくなる（[TN2406](https://developer.apple.com/library/archive/technotes/tn2406/_index.html)）
- Android は、裏に回したアプリを OS がメモリ不足などで終了させ、ユーザーが戻ったときに画面を開き直すことがある。ViewModel を含めメモリの中身は消えるので、戻したい小さな値は SavedStateHandle に退避する。Google もこの使い方を推奨している（[Save UI states | Android Developers](https://developer.android.com/topic/libraries/architecture/saving-states)）
- SavedStateHandle の中身はプロセスの間で受け渡され、その受け渡しには合計で約 1MB の上限がある。超えるとクラッシュする（[TransactionTooLargeException | Android Developers](https://developer.android.com/reference/android/os/TransactionTooLargeException)）。画像のデータは入れられない
- ユーザーが最近使ったアプリの一覧からスワイプしてアプリを終了させた場合は、退避した値は捨てられ、最初の画面から始まる（Save UI states）。クラッシュした場合も最初の画面から始まる（未確認）
- iOS は、標準では、終了させたアプリの画面を開き直さない。状態を戻す仕組み（State Restoration）はあるが、アプリが自分で作り込む前提。CMP の iOS 版で、SavedStateHandle の値がアプリの終了後にも戻るかは未確認
- ViewModel が破棄されるのは、その画面が画面の履歴から取り除かれたとき（戻る操作で閉じたときなど）。別の画面やピッカーを開いている間、画面を回転させたときは破棄されない（Android）。CMP の iOS 版で同じように破棄されるかは未確認
- `viewModelScope` で始めた処理は、ViewModel が破棄されるとキャンセルされる（[Kotlin coroutines with lifecycle-aware components | Android Developers](https://developer.android.com/topic/libraries/architecture/coroutines)）
- 撮ったままの写真は1枚あたり数 MB、縮小すると数百 KB 程度になる（目安。測っていない）
