# Recipe の写真の扱い

Recipe の写真をどう選び、どこに置き、いつ消すかをまとめたファイルです。
写真はまだ実装していません。
写真を実装する PR では、このファイルを読んでから着手し、決めたことをこのファイルに反映します。

## 決まったこと

- 写真は、名前・状態・メモと同じく、編集画面の保存ボタン1回でまとめて反映する想定
- 選んだ写真は、アプリ専用フォルダの中の仮置きの場所にコピーする。Recipe の保存に成功したときに、本番の場所へ移す
  - 仮置きの場所は、写真を実装するときに見直してよい
- 仮置きの写真は、写真を選び直したとき、写真を削除したとき、保存せずに編集画面を閉じたときに、その場で消す。Recipe の保存に失敗したときは、もう一度保存できるように残す
- 写真は縮小できるならしたい。どこまで縮小するかは、UI に表示して動かしてから決める
- 起動時に削除して、起動速度を落とすことは避けたい
- 保存の途中で落ちたときに本番の場所に残る写真の掃除は、後回しにする
- 写真を選ぶ・撮る UI は、FileKit を使うか自作するかを決めずにおく。FileKit はまだ 0.x のため、カメラも含めて各プラットフォームの UI を抽象化して自作する可能性も残す

## まだ決めていないこと

- 写真のファイルを本番の場所へ移す処理と、古い写真を消す処理を、UseCase・data 層・UI のどこが持つか。編集の UseCase が写真をどう受け取るかも、これで決まる
- Recipe の保存に失敗したときに、仮置きの写真を残す方法。本番の場所へ移した後に Recipe の保存が失敗するため、移した写真を戻すか、移さずにコピーして成功してから仮置きを消すかを決める
- 編集中に Android が裏でアプリを終了させたとき、選んだ写真を戻すか
  - 戻す場合は、仮置きの ID を SavedStateHandle に退避し、仮置きが無かったときの扱いを足す。戻さない場合に作った部分は作り直さずに済む
  - 確かめ方は、Android は裏に回してから `adb shell am kill <パッケージ名>` で終了させ、最近使ったアプリから戻る。iOS はシミュレーターで終了させて起動し直し、最初の画面から普通に始まることを確かめる
- 仮置きの写真を、いつ掃除するか。起動時の削除は避けたい
- 写真の参照に何を入れるか（アプリが振る ID か、相対パスか）と、その型（値クラスにするか）。絶対パスは使えない（下の事実を参照）

## 前提になる事実

- 写真は、OS から期限付きで届く
  - iOS のピッカーは写真を一時ファイルで渡し、受け取りの処理が終わると OS が消す
  - Android のピッカーが渡す URI は、標準ではアプリが終了するまでしか読めない。読める期間を延ばす方法はあるが、アプリ全体で最大 5,000 件まで
  - Android のカメラは、アプリが用意したファイルに写真を書き込む
- アプリがいつでも読み書きできるのは、アプリ専用フォルダだけ。ギャラリーは、ピッカーで選ばれた写真だけを期限付きで読める
- ギャラリーの元の写真をコピーせずに参照し続ける方法もある（Android は URI の権限を延ばす、iOS は写真ライブラリの許可を得て識別子を持つ）。仮置きにコピーする方針にしたので、ギャラリーで元の写真を消したり編集したりしても、Recipe の写真は変わらない
- iOS では、アプリを更新するとアプリのフォルダの絶対パスが変わる。絶対パスを保存すると、更新後に写真が見つからなくなる
- Android は、裏に回したアプリを OS が終了させ、後で画面を開き直すことがある。メモリの中身は消えるので、戻したい値は SavedStateHandle に退避する。SavedStateHandle は全部で約 1MB までで、画像のデータは入れられない
- iOS は、標準では終了させたアプリの画面を開き直さない。CMP の iOS 版で、SavedStateHandle の値がアプリの終了後にも戻るかは確認していない
- アプリがクラッシュしたときや、ユーザーがアプリを終了させたときは、Android でも退避した値は使われず、最初の画面から始まる
