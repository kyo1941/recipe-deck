# Recipe の写真の扱い

Recipe の写真をどう選び、どこに置き、いつ消すかの検討をまとめたファイルです。
写真機能は現時点では未実装です。
写真を実装する PR では、必ずこのファイルを読んでから着手します。
実装して方針が固まったら、残すべき方針を [architecture.md](architecture.md) に移し、このファイルは削除します。

このファイルは、architecture.md の写真の部分を詳しくしたものです。
層の分け方や失敗の扱いは、architecture.md の「UseCase の方針」「データ層の方針」に従います。
このファイルと architecture.md の記述が食い違った場合は、architecture.md を正とします。

各項目には、次のステータスを付けています。

- **決定**：採用・決定した事項
- **方針**：現時点での設計方針（決定者の意図に基づくが、今後の計測や実装結果によって覆りうる）
- **保留**：現時点では決定しないと判断した事項（保留とする理由および、決めるときの判断材料を記載）
- **想定**：確定ではないが、現時点で前提として進めている仮説・見通し
- **未決**：まだ判断していない事項（議論済みのものを含む）

## 用語の定義

- **アプリ専用フォルダ**：Android の `filesDir`、iOS の Application Support のように、アプリのみが読み書きでき、OS から自動削除されない領域。キャッシュ用フォルダ（Android の `cacheDir`、iOS の Caches）もアプリ専用領域ではあるが、ストレージ容量不足時に OS によって自動削除されるため、このファイルの定義には含めない
- **仮置き**：選んだ写真について、Recipe の保存が完了するまで一時的に配置しておく場所およびそのファイル。Recipe からはまだ参照されていない状態
- **本番の場所**：Recipe の写真として正式に利用するファイルを永続的に配置する場所
- **アプリの強制終了**：クラッシュ、OS によるプロセスの終了（kill）、ユーザーによるタスク終了のいずれも含む。いずれのケースでもメモリ上のデータは消失するがローカルファイルは残る。ViewModel の破棄処理（`onCleared` 等）が呼ばれることは保証されないため、呼ばれない前提で扱う
- **起動処理**：アプリのプロセス起動から初期画面が表示されるまで。Android でプロセスが終了された後に画面が開き直される場合は、その画面の表示完了までを指す

## 想定している流れ

1. 編集画面で、写真を選ぶ（または撮る）
2. 写真を、アプリ専用フォルダの中の仮置きの場所にコピーする（決定）
   - 編集画面の UI 状態（UiState）は画像バイナリを直接保持せず、写真を指す ID のみを保持する。Recipe に既に設定されている既存写真なら本番の写真 ID、新しく選んだ写真なら仮置きの写真 ID を持つ（決定）
3. 写真を選び直す、写真を削除する、保存せずに編集画面を閉じる、のいずれかが行われたら、その場で仮置きファイルを削除する（決定）
4. 保存ボタンを押したら、「仮置きの写真を本番の場所に置く → Recipe を保存する → 古い写真を削除する」の順に進む（想定）
   - 本番の場所に置くとき、仮置きファイルを移動（Move）するかコピーするかは未決
5. Recipe の保存に失敗したら、もう一度保存できるように仮置きファイルを残す（決定。残す具体的な実装方式は未決）

写真についても、名前・状態・メモと同じく、編集画面の保存ボタン1回でまとめて反映すること（想定）を前提にしています。
本番の場所もアプリ専用フォルダの中に置くこと（想定）を前提にしています。

## 決めたこと

### 選んだ写真は仮置きにコピーし、保存のときに本番の場所に置く（決定）

保存ボタンを押すまで写真を手元に保持し続けるには、OS から期限付きで提供された写真を、アプリが自分の管理する場所（メモリかファイル）へ写し取っておく必要があります（後述の「前提になる事実」参照）。
退避先および管理方式として、同一の状況（既存写真 old が設定された Recipe を編集し、写真 X を選択後、写真 Y に選び直して保存する）を想定し、以下の4方式を比較・検討しました。

- **A. 画像データをそのままメモリ（ViewModel）に保持する**
  - 選び直す・削除する・閉じる・アプリ終了のどの場面でも写真はメモリ解放とともに自然に破棄され、アプリ側でのファイル削除処理は不要
  - 保存に失敗しても、写真データはメモリに残るため再試行が容易
  - Android でアプリがバックグラウンド時に終了させられたとき、選んだ写真は復元できない（SavedStateHandle に画像バイナリは入らないため）
  - 編集中は、画像データを画面状態としてメモリに保持し続ける必要がある（縮小処理を行えば数百 KB 程度となる見込み）
- **B. 選んだ瞬間に本番の場所へコピーする**
  - 保存ボタン押下時にファイルを配置する処理が不要であり、保存に失敗しても写真データはそのまま保持される
  - 選び直す・削除する・閉じる場面では、アプリがその場でファイルを削除する必要がある
  - アプリの強制終了時に不要な残存ファイルが正式な写真ファイルと同じ場所に混在し、クリーンアップするには DB 内の全 Recipe の写真 ID と照合する必要がある
- **C. 選んだ瞬間に仮置きの場所へコピーし、保存ボタンで本番の場所に置く**
  - 選び直す・削除する・閉じる場面では、アプリがその場で一時ファイルを削除する必要がある（B と同様）
  - アプリの強制終了時に残った不要ファイルは仮置き領域にのみ存在するため、DB と照合することなく作成日時などの条件だけで安全に削除できる
  - アプリの強制終了からの復帰時に写真を復元する要件が生じた場合も、ID を退避しておけば仮置きファイルから復元できる
  - Recipe の保存に失敗したときに仮置きファイルを残す方法を、別途設計する必要がある（本番の場所に置く際に仮置きファイルを移動させると、仮置き側には存在しなくなるため）
- **D. 端末ギャラリーの元の写真をコピーせず、参照のみを保持し続ける**
  - ユーザーがギャラリー側で元の写真を編集・削除すると、Recipe の写真も変更・消失してしまう
  - クラウドストレージ上にのみ存在する写真は、表示のたびにネットワーク取得が必要になることがある
  - 複数端末での同期や将来的なサーバー保存を行う際は、結局どこかで画像データを読み込んでアップロードする必要がある
  - カメラで撮影した写真はギャラリーに存在しない
  - Android は URI の読み取り権限を保持できる件数がアプリ全体で最大 5,000 件までであり、iOS はアクセス許可ダイアログが表示される

ユーザーが、A・B・C の比較表を見たうえで方針 C を選び、D を提示した後も C を維持しました。
ユーザーは、C を選んだ決め手を述べていません。
比較表から読み取れる方針 C の主な利点は、アプリの強制終了時に残存する不要ファイルが正式な保存ファイルと混在しない点、およびアプリの強制終了時に写真を復元する設計余地を残せる点（復元対応自体の要否は保留）にあります。一方で、Recipe 保存失敗時に仮置きファイルを残す方法を設ける必要があります。

なお、最初に C が選ばれた時点では、Claude が A の欠点として「画像データが数 MB に達する」「data class の等価性判定が意図通りに動かない」を挙げていました。
これは言い過ぎで、縮小処理を行えば数百 KB 程度に抑えられること、また選択ごとに新しいインスタンスが生成されるため等価性判定も決定的な問題ではないことを、後から訂正しています。
訂正の後に比較表を並べ、ユーザーは C を維持しました。

仮置き領域の配置場所は、アプリ専用フォルダ内とします（決定）。
OS による意図しない自動削除を受けず、アプリが明示的に削除したタイミングでのみ消去されるようにするためです。
キャッシュ用フォルダを採用した場合、削除漏れしたファイルを OS が回収してくれるメリットはあるものの、編集中に OS によってファイルが削除されるリスクがあり、その例外処理が必要となります。
写真機能の実装時に、キャッシュ用フォルダを採用する案も含めて見直してよい、とユーザーが決めています。

アプリ専用フォルダにファイルをコピーして管理するため、ユーザーがギャラリー側で元の写真を編集・削除した場合でも、Recipe に設定された写真には影響しません。

### 仮置きは、不要になったと判明した場面でその場で消す（決定）

| 状況・契機 | アプリ側での検知可否 | 仮置きファイルの扱い |
|---|---|---|
| 写真を選び直した | 検知可能 | 直前の仮置きファイルを削除 |
| 選んだ後に「写真を削除」を押した | 検知可能 | 削除 |
| 保存せずに編集画面を閉じた | 検知可能（ViewModel 破棄時） | 削除 |
| 保存に成功した | 検知可能 | 残さない（移動した場合は処理不要、コピーした場合は削除） |
| 保存に失敗した | 検知可能 | 再度保存できるように残す |
| 編集中にアプリが強制終了した | 検知不可 | 後続のクリーンアップ処理で回収（後述の「まだ決めていないこと」参照） |

発生した瞬間に検知できる場面については、その場で削除処理を実行すれば確実にクリーンアップできる、と判断しました。
なお、ViewModel が破棄されるときのライフサイクル処理について、CMP の iOS 版でも Android と同様に動作するかは現時点で未確認です。

### 起動処理シーケンス内では、写真を削除しない（方針）

起動速度を低下させたくない、というユーザーの意思による方針です（どれだけ遅くなるかは未計測）。
アプリの強制終了時に残存する仮置きファイルや、本番の場所の写真のクリーンアップにも、この方針を適用します。
今後実装・計測を行い、起動処理の中で削除を行っても影響が無視できると分かった場合は、見直しを可能とします。

クリーンアップを実行するタイミングの候補としては、以下が挙げられています。

- 初期画面の表示完了後に、バックグラウンドスレッドで削除処理を実行する。処理内容はファイル一覧の取得と、DB からの写真 ID 一括読み取りのみであり、写真が数百枚程度なら体感できる負荷にはならない見込み（未計測）
- Recipe の保存に成功した後に実行する
- アプリがバックグラウンドに回ったときに実行する
- OS の定期実行の仕組みを使う（Android の WorkManager、iOS の BGTaskScheduler）。Android と iOS で別々の実装になる

起動処理の完了後に非同期でクリーンアップを行う場合、ユーザー操作との競合（並行処理）に留意する必要があります。

- 本番の場所のクリーンアップと保存：本番の場所にファイルを配置した直後、Recipe を保存する前の写真は、まだどの Recipe からも参照されていない。このタイミングでクリーンアップが実行されると誤って削除してしまうため、クリーンアップと保存処理の排他制御（直列化）を行うか、保存操作が可能になる前にクリーンアップを完了させる
- 仮置きのクリーンアップと写真を選ぶ操作：起動後、クリーンアップが走る前に新しく選んだ写真も仮置きに入るため、「今回の起動より前に作成されたファイルのみを削除対象とする」などの条件で区別する

### 写真は縮小できるならしたい（方針）

撮影したままの写真は1枚あたり数 MB 程度になります（目安）。
縮小・圧縮すれば端末ストレージの消費および将来的なサーバー同期時の通信負荷を軽減できますが、代わりに拡大時の精細度が低下します。
ユーザーは、縮小できるならしたいが、どこまで縮小できるかは UI に表示して動かしてみないと分からない、と述べています。
どこまで縮小するか（そもそも縮小できるか）は、実際の UI 表示を確認した上で決定します。

## 今は決めないと決めたこと

### Android でバックグラウンド待機中に OS によりプロセス終了させられた際、選択中の写真を復元するかどうか（保留）

編集中に写真を選び、保存せずに別アプリへ切り替えている間に、Android のメモリ回収によってアプリが終了させられることがあります。
ユーザーが復帰した際、Android は編集画面を開き直しますが、メモリ上のデータは消失しています。
（※ iOS は標準では終了したアプリの画面を開き直しません。また Android でも、ユーザーがタスク一覧から明示的に終了させた場合は初期画面から始まります。クラッシュ時も同様と想定されますが未確認です）

- **復元しない**：写真は元の未編集時の写真に戻り、ユーザーは必要なら選び直す。退避した ID が存在しないため、「退避 ID はあるのに仮置きファイルが無い」場合の例外処理が不要となる
- **復元する**：仮置き写真の ID を SavedStateHandle に退避し、画面再生成時に仮置きファイルから復元する。起動後のクリーンアップ処理で復元予定の仮置きファイルを誤って削除しないための保護条件（作成から一定時間以上経過したもののみ削除するなど）や、仮置きファイルが消失していた場合の表示・保存時の例外処理が必要となる

今決めなくてよい理由：どちらを選択しても、名前・状態・メモの基本編集機能には影響しないため。
写真機能の実装時に判断します。
初期実装を「復元しない」で作った後に「復元する」へ変更する場合も、追加が必要なのは以下の3点のみであり、根本的な手戻りは発生しません。

- 仮置き写真の ID を退避し、開き直したときに復元する処理
- 仮置きファイルのクリーンアップ条件（今回の起動より前のファイルを削除する条件に加え、一定時間以上経過したもののみを削除する条件を追加）
- 「仮置きファイルが無い」という失敗結果の追加。本番配置処理を UseCase が持つ場合、編集 UseCase の結果型にこの失敗を追加する（結果型に追加することで、それを受け取る `when` 式で網羅性チェックが働き、対応漏れをビルド時に検知可能）

判断時の検証方法：

- Android の単体テスト：仮置き ID を格納した SavedStateHandle で ViewModel を生成し、写真が復元された状態になるかを検証する
- Android の実機検証：アプリをバックグラウンドに回し、`adb shell am kill <パッケージ名>` で終了させ、最近使ったアプリ一覧から復帰する。（開発者向けオプションの「アクティビティを保持しない」は画面を破棄するだけでプロセス自体は終了させないため、本検証の確認手段としては不十分）
- iOS シミュレーター検証：アプリをバックグラウンドに回して終了させ（Xcode の停止、または `xcrun simctl terminate`）、起動し直す。初期画面から通常起動すること、および CMP の iOS 環境で SavedStateHandle の値が復元されるか（未確認）を検証する
- どちらの結果であっても、「退避した ID が無い」場合と「ID はあるのに仮置きが無い」場合をハンドリングできていれば不具合にはならない

### 保存処理の途中でアプリが強制終了した際に本番保存先に残る孤立写真のクリーンアップ（保留：今は作らない）

保存ボタン押下後の一連の処理の途中でアプリが強制終了すると、どの Recipe からも参照されない写真が本番の場所に1枚残ることがあります。
本番の場所に配置した後、Recipe を保存する前に強制終了した場合は新規写真が残り、Recipe 保存後、古い写真を削除する前に強制終了した場合は古い写真が残ります。

これを削除・整理するには、本番保存先のファイルを DB 内の全 Recipe の写真 ID と照合し、参照されていないファイルを特定して削除する必要があります（GC と同様の考え方）。
そのために、全 Recipe の写真 ID を取得する処理を Repository に追加し、保存処理と同時に走らないよう排他制御を行う必要があります。

現時点で作らない理由：発生はまれで、実害もわずかなストレージ消費にとどまるため。
後から機能追加する場合も、追加が必要なのはクリーンアップ処理と Repository の読み取り処理が中心です（クリーンアップと保存を排他制御（直列化）する場合は、保存処理側にも改修が必要となります）。
ユーザーが後回しを選びました。
参照されない写真による容量圧迫が問題になった段階、またはサーバー同期等で写真保存の仕組みを大きく刷新するタイミングで実装します。

### 写真を選ぶ・撮る UI に、ライブラリを採用するか自作するか（保留）

- **FileKit**：KMP / CMP 向けライブラリ。ピッカー、アプリ専用フォルダ（`FileKit.filesDir`）、画像の圧縮、表示用ライブラリ Coil との連携機能がある。バージョンは 0.x 系。カメラに対応しているかは README からは確認できない（リリースノートに iOS のカメラ表示修正の記載があるため、対応していると推測される）
- **Peekaboo**：CMP 向けライブラリ。ピッカー、カメラ撮影、縮小・圧縮に対応
- **自作**：選択対象は写真1枚のみであるため、各プラットフォームのピッカーとカメラ UI を抽象化して自前実装可能。ただし、画像処理まわりの実装負荷の見積もりが未確定

FileKit が 0.x 系である点、カメラ撮影への対応要件がある点、画像処理まわりの自作時の工数が見積もれていない点から、自作の選択肢も排除せず保留とする、とユーザーが判断しました。
写真 UI の実装時に、FileKit のカメラ対応状況、iOS のカメラで撮った写真がどの形式で渡されるか、自作の開発コストを比較・検証した上で決定します。

## 写真の実装に着手するときに決めること

上記の保留事項3点と、後述の「まだ決めていないこと」に加えて、次の事項も決定します。

- どこまで縮小するか（解像度・圧縮率のしきい値）
- 仮置きの場所を見直すか（キャッシュ用フォルダにする案も含めて）
- 写真の編集を、名前・状態・メモと同一の編集 UseCase に統合するか

設計の順序として、まず「どの段階で写真を実装するか」と「本番配置の処理責務をどの層が持つか」の2点を確定させることで、付随する他の検討事項を絞り込むことができます。

- 「どの段階で写真を実装するか」（architecture.md の「実装の進め方」のどこに入れるか）により、UI からデータ層まで一貫して作成するのか、ドメイン層と UseCase 層のみを先行して作成するのかが決まる
- 「本番配置の処理責務をどの層が持つか」により、以下の設計が決定または絞り込まれる：
  - 編集 UseCase が写真をどのような形式で受け取るか
  - 仮置きへのコピーと削除をどの層が担うか、仮置き ID の採番をどこで行うか
  - 写真関連の失敗をどの型で表現するか、写真用の Repository を分離するか
  - 保存失敗時に仮置きファイルを残すリカバリ処理をどの層に実装するか

### 議論したが、決めていないもの（未決）

**仮置き写真の本番配置処理および古い写真の削除処理を、どの層（コンポーネント）の責務とするか**

- UseCase が持つ
  - 写真のファイルを扱う interface を domain 層に定義し、UseCase はそれと Recipe の Repository の2つを利用する
  - 処理シーケンスの順序や途中で失敗したときの扱いが UseCase 内に明示され、単体テストで検証しやすくなる
  - 写真操作に起因する失敗が UseCase の結果型に加わる
  - UseCase は写真を「維持（そのまま）」「差し替え（仮置き ID 指定）」「削除」の3種類で受け取る形になる（`String?` で受け取ると、既存の本番 ID なのか仮置き ID なのかを識別する必要が生じるため）
- data 層（Recipe の Repository の実装）が持つ
  - 保存処理の内部で写真の変更有無を検知し、ファイルを本番の場所に配置したり古い写真を削除したりする
  - Recipe の `photoRef` は本番写真を指すものであるため、新規選択した仮置き写真を Recipe に直接格納して渡すことはできない（保存メソッドに何を渡すかを再検討する必要がある）
  - 「Recipe を保存する」処理の中にファイル I/O 操作が入り、DB 保存の失敗とファイル操作の失敗が混在する。処理シーケンスの順序や途中で失敗したときの扱いが UseCase からは見えなくなる
- UI（ViewModel）が持つ
  - 保存ボタンを押したときに、ViewModel が仮置きの写真を本番の場所に配置し、UseCase を呼び出して保存し、成功後に古い写真を削除する
  - UseCase は本番写真の ID を受け取って保存するだけのシンプルな責務となる
  - ViewModel が保存先ストレージ構造を意識する必要があり、本番配置処理の失敗ハンドリングや Recipe 保存失敗時のロールバック処理も ViewModel 側で扱うことになる
  - architecture.md の「ViewModel は例外を catch せず、結果を UiState に変換するだけにとどめる」という設計方針と衝突する（採用する場合はその方針を見直す必要がある）

**Recipe の保存に失敗したときに、仮置きファイルを残す方法**

- 移動した写真を仮置きへ戻す（移動方式）：ファイル実体は常に1つに保たれるが、戻す処理そのものが失敗したときの例外ハンドリングが必要となる
- 移動ではなくコピーを行い、Recipe の保存に成功してから仮置きファイルを削除する（コピー方式）：保存失敗時でも仮置きファイルはそのまま保持されるが、成功後の仮置き削除に失敗した場合に不要な一時ファイルが残存する

**編集中にアプリが強制終了した際に残存する仮置きファイルを、いつ、どのような条件で削除（クリーンアップ）するか**

- 起動処理シーケンス内では削除しない（方針）。クリーンアップタイミングの候補は前述の「起動処理シーケンス内では、写真を削除しない」を参照
- クリーンアップ処理の実行前に新しく選ばれた写真を誤って削除しないための識別条件が必要となる（例: 今回の起動時刻より前に作成された仮置きファイルのみを削除対象とする等）
- 強制終了時に写真を復元する設計を採用した場合は、さらに復元対象として保持すべき仮置きファイルを保護する条件判定が必要となる

**写真の参照（Recipe の `photoRef: String?`）に格納する値の形式および型定義**

- アプリ独自の採番 ID（例：`3f2a9c`）：ファイル名やディレクトリ構成が変更されても DB レコードの値は影響を受けない。将来的にサーバーへアップロードした際も同一 ID でサーバー上の写真を指すことができる。画面表示時には ID からファイルの物理パスを解決するマッピング処理が必要となる（解決責務の配置場所は未議論）
- 相対パス（例：`photos/3f2a9c.jpg`）：iOS のアプリアップデートによるサンドボックスパス変更でも破損しない。ただしディレクトリ構成が DB に保存されるため、フォルダ構造を変更する際には既存データのマイグレーションが必要となる
- 絶対パス：採用不可（後述の「前提になる事実」を参照）

型を、他の ID と同様に文字列をラップする値クラス（value class）にするかも未定です。
値クラス化することで、仮置き ID と本番 ID を型安全に区別することが可能となります。

## 前提になる事実

2026-10-05 時点での調査結果に基づく情報です。
（※「未確認」と記載した項目は、未調査であるか、公式ドキュメント等の出典で検証できていない項目です）

- 写真は、OS から期限付きで提供される（一時ファイル、または期限付きの読み取り権限として）
  - iOS の写真ピッカー（PHPicker）は、写真を一時ファイルとして渡し、受け取りハンドラ処理の完了に伴い OS がそのファイルを削除する。そのため、ハンドラ処理の中でアプリ専用の領域へコピーする必要がある（[Apple Developer Forums](https://developer.apple.com/forums/thread/652695) 参照）
  - Android の写真ピッカーが返すのは、実ファイルパスではなく `content://` スキームの URI。標準では、端末の再起動またはアプリプロセスの停止までしか読み取り権限が持続しない。`takePersistableUriPermission` により権限の有効期間を延長できるが、アプリ全体で最大 5,000 件までの上限があり、超過すると古いものから無効化される（[Photo picker | Android Developers](https://developer.android.com/training/data-storage/shared/photo-picker) 参照）
  - Android のカメラ（外部カメラアプリを起動して撮影を依頼する方法）は、アプリ側が事前に用意した出力先ファイル URI に撮影データを書き込む
  - iOS のカメラで撮影した写真がどのような形式で渡されるかは未調査
- アプリが恒常的に（制限なく）読み書きできるのは、アプリ専用フォルダに限られる。端末ギャラリー内の写真は OS が管理しており、アプリが直接ファイルパスで開くことはできない。ピッカーで選択された写真についてのみ、一時的な読み取り権限が付与される
- ギャラリー内の元の写真を参照し続ける場合、Android は URI の読み取り権限を永続化する必要がある。iOS はフォトライブラリへのアクセス許可をユーザーから得た上で、写真の識別子（`localIdentifier`）を保持する必要がある。この際、アクセス許可を求めるダイアログが表示され、ユーザーは選択した写真のみにアクセスを制限することもできる
- iOS では、アプリアップデート時にサンドボックス（アプリのコンテナフォルダ）の絶対パスが変動する。内部のファイル実体は維持されるが、絶対パスを DB 等に永続化していると参照不能となる（[TN2406](https://developer.apple.com/library/archive/technotes/tn2406/_index.html) 参照）
- Android は、バックグラウンドに移行したアプリを OS がメモリ逼迫等によりプロセス終了（kill）させ、ユーザーが復帰した際に画面を開き直すことがある。ViewModel を含むメモリデータは消失するため、復元したい軽量な状態値は SavedStateHandle に退避する。Google 公式もこの設計パターンを推奨している（[Save UI states | Android Developers](https://developer.android.com/topic/libraries/architecture/saving-states) 参照）
- SavedStateHandle のデータはプロセス間通信（IPC）を経由して受け渡されるため、全体で約 1MB のサイズ上限（Binder トランザクション制限）が存在する。これを超過するとクラッシュ（`TransactionTooLargeException`）を引き起こすため、画像バイナリを直接格納することはできない（[TransactionTooLargeException | Android Developers](https://developer.android.com/reference/android/os/TransactionTooLargeException) 参照）
- ユーザーがマルチタスク画面（最近使ったアプリ一覧）からスワイプしてアプリを終了させた場合は、退避した状態は破棄され、次回は初期画面から起動する（Save UI states 参照）。クラッシュした場合も次回は初期画面から起動すると想定される（未確認）
- iOS は、標準では終了したアプリの画面を開き直さない。状態を復元する仕組み（State Restoration）は存在するが、アプリ側で個別実装することが前提となる。CMP の iOS 環境において、SavedStateHandle の値がアプリ終了後にも復元されるかは未確認
- ViewModel が破棄されるのは、該当画面がバックスタックから完全に取り除かれたタイミング（戻る操作で閉じたとき等）である。別の画面やピッカーを開いている間、あるいは画面回転時には破棄されない（Android）。CMP の iOS 環境において同様に破棄されるかは未確認
- `viewModelScope` で開始したコルーチン処理は、ViewModel が破棄されると自動的にキャンセルされる（[Kotlin coroutines with lifecycle-aware components | Android Developers](https://developer.android.com/topic/libraries/architecture/coroutines) 参照）
- 撮影したままの写真は1枚あたり数 MB 程度、縮小・圧縮すると数百 KB 程度になる（目安。実測値ではない）
